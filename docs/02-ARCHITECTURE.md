# 02 — Architecture

## 1. Big picture
```
 Guest phone ─┐                         ┌─ Supabase Postgres (RLS + RPCs = business rules)
 Waiter tab ──┼─ Next.js 16 on Vercel ──┼─ Supabase Auth (anonymous guests, email staff)
 Kitchen TV ──┤   (RSC + route handlers)├─ Supabase Realtime (postgres_changes, RLS-filtered)
 Admin ───────┘                         └─ Supabase Storage (menu images)
                     │
                     └─ SSLCommerz (bKash, Nagad, cards, internet banking) ── IPN ─▶ /api/payments/sslcommerz/ipn
```
- **Postgres is the brain.** Pricing, the order state machine, permissions, billing and
  idempotency live in SQL functions (`docs/sql/0001_init.sql`, already tested by
  `docs/sql/db-smoke-test.mjs`, 43 checks). The Next.js app is a thin, beautiful shell.
- **Clients read with RLS-scoped selects and write with RPCs.** Browser clients call
  RPCs directly with the user's JWT (fast, no extra hop). Server-only operations
  (payments, staff management) run in route handlers / server actions.
- **Realtime = invalidate + refetch.** Simple, correct after reconnects, no drift.

## 3. Supabase clients
- `lib/supabase/client.ts` — `createBrowserClient(url, publishableKey)`; singleton.
- `lib/supabase/server.ts` — `createServerClient` with Next `cookies()` (async in Next 16).
- `lib/supabase/admin.ts` — `import 'server-only'`; `createClient(url, SECRET_KEY,
  { auth: { persistSession: false } })`. Used only for: payment init/IPN/return,
  staff create/update, QR rotation (could also be RLS), demo seeding.
- `proxy.ts` — refreshes the auth cookie on every request (official @supabase/ssr
  pattern) and redirects unauthenticated users away from `/staff`, `/kitchen`,
  `/admin` to `/login?next=…`. Role checks happen in each section's server `layout.tsx`
  (query `staff_members` for `auth.uid()`; anonymous users are never staff).
- Keys: use the new Supabase key types — `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
  (`sb_publishable_…`) and `SUPABASE_SECRET_KEY` (`sb_secret_…`). If the project only
  has legacy anon/service_role keys, they work in the same slots.

## 4. Auth
**Guests**: on first load of `/t/[token]`, if no session → `supabase.auth.signInAnonymously()`
(with `captchaToken` from invisible Cloudflare Turnstile when `NEXT_PUBLIC_TURNSTILE_SITE_KEY`
is set). Then `rpc('join_table', { p_qr_token })`. Store `{session_id, table_label, …}`
in a React context. Enable anonymous sign-ins in `supabase/config.toml`
(`[auth] enable_anonymous_sign_ins = true`) and in the dashboard for production.

**Staff**: email + password (`signInWithPassword`). Accounts created by an
owner/manager in Admin → server action uses admin client `auth.admin.createUser`
(email_confirm: true) + insert `staff_members`. Server action re-checks the caller's
role (managers cannot create/modify owners). Deactivation sets `is_active=false` and
signs the user out (`auth.admin.signOut`).

**Same device, both roles**: a logged-in staff member who scans a QR simply joins as
themselves — `join_table` only needs `auth.uid()`.

## 5. Data access patterns
| Need | How |
|---|---|
| Guest menu | RSC fetch (publishable key, anon-readable) + `revalidateTag('menu')` on admin edits; client keeps it in TanStack Query for live sold-out updates |
| Guest session data | client `select` on `orders`, `order_items`, `service_requests`, `payments` filtered by `session_id` (RLS limits to their table) + `rpc('session_bill')` |
| Floor | `rpc('floor_snapshot')` (one round-trip) + order details on demand |
| Kitchen | `select orders (+order_items)` where `status in (in_kitchen, preparing)` or `ready` within 10 min |
| Admin lists | server components with server client; mutations via server actions → `revalidatePath` |
| Reports | `rpc('sales_report', { p_from, p_to })` |

Query keys live in `lib/query-keys.ts`, e.g. `qk.session(id)`, `qk.sessionOrders(id)`,
`qk.bill(id)`, `qk.floor()`, `qk.kitchen()`, `qk.menu(restaurantId)`.

## 6. Realtime
`useRealtimeInvalidate({ channel, listeners: [{ table, filter? }], keys })`:
subscribes to `postgres_changes` for each listener, and on any event calls
`queryClient.invalidateQueries` for the keys (debounced 150 ms to batch bursts).
On `SUBSCRIBED` after a reconnect, on `visibilitychange` → visible, and on `online`,
it invalidates everything for that screen. While the channel status is not
`SUBSCRIBED`, show `ConnectionBanner` and poll every 10 s.

| Screen | Channel | Listens to (filter) |
|---|---|---|
| Guest | `guest:{session_id}` | orders, service_requests, payments (`session_id=eq.{id}`); table_sessions (`id=eq.{id}`); order_items (no filter, RLS-scoped); menu_items (`restaurant_id=eq.{rid}`) |
| Floor | `floor:{restaurant_id}` | orders, service_requests, table_sessions, payments, order_items (`restaurant_id=eq.{rid}` where the column exists) |
| Kitchen | `kitchen:{restaurant_id}` | orders, order_items |

The browser client must be authenticated before subscribing (RLS applies to realtime).
Tables are already in the `supabase_realtime` publication (migration).

Alerts for staff are derived by diffing the previous and new query data (e.g. a new
`placed` order id appeared → chime + toast + table pulse), never from raw events.

## 7. Payments (SSLCommerz — covers bKash, Nagad, cards, internet banking)
Provider abstraction `PaymentGateway { createSession(input), validate(valId) }`.
Selected by `PAYMENT_GATEWAY=sslcommerz|mock`. `env.ts` refuses `mock` when
`VERCEL_ENV === 'production'`.

**Init** `POST /api/payments/sslcommerz/init` (guest JWT in Authorization header or
cookie) body `{ session_id, amount_minor?, channel? }`:
1. With the user's client: `rpc('session_bill')` (proves guest membership); reject if
   `unconfirmed_orders > 0` or `due_minor = 0`; amount = requested (≤ due) or due.
2. Admin client: insert `payments` row (`method='sslcommerz'`, `channel`, `status='initiated'`,
   `tran_id = 'ES-' + nanoid(16)`).
3. Call the SSLCommerz session API (`/gwprocess/v4/api.php`, sandbox or live host
   from env) with `total_amount = (amount_minor/100).toFixed(2)`, `currency=BDT`,
   `tran_id`, `success_url/fail_url/cancel_url = {APP_URL}/api/payments/sslcommerz/return?r=…`,
   `ipn_url = {APP_URL}/api/payments/sslcommerz/ipn`, `value_a = session_id`,
   `value_b = table qr token`, product fields, placeholder customer fields from
   restaurant settings, `shipping_method=NO`, and `multi_card_name` to pre-select the
   chosen channel when SSLCommerz supports it (verify values in their docs).
4. Return `{ url: GatewayPageURL }`; client does `window.location.assign(url)`.

**IPN** `POST /api/payments/sslcommerz/ipn` (form-encoded, server-to-server):
1. Parse `val_id`, `tran_id`. Call the **Validation API**
   (`/validator/api/validationserverAPI.php?val_id&store_id&store_passwd&format=json`).
2. Accept only if validation `status` is `VALID` or `VALIDATED`, `tran_id` matches,
   `currency_type`/`currency` is BDT, and amount (×100, rounded) equals our row.
3. `risk_level = 1` → `mark_gateway_payment(…, 'pending_review', …)` (staff must verify).
   Otherwise `'paid'`. Failed/cancelled/expired → mark accordingly.
4. Always respond 200 quickly after processing; the RPC is idempotent.

**Return** `POST|GET /api/payments/sslcommerz/return?r=success|fail|cancel`:
the customer's browser is POSTed here cross-site, so **auth cookies are not sent**
(SameSite=Lax). Do not rely on the user session: read `tran_id`/`val_id` from the
form, validate exactly like the IPN (idempotent), look up `value_b` (table token),
then `303` redirect to `/t/{token}/payment/result?status=…&tran=…`.

Never mark anything paid from the browser alone. Never trust amounts from the form.

Cash: staff `rpc('record_cash_payment')`. Guests choosing cash just create a
`request_bill` service request with note "Paying cash".

## 8. Errors
`lib/errors.ts` maps Postgres messages/codes to i18n keys:
`ITEM_UNAVAILABLE:<name>` → "{name} just sold out", `SESSION_CLOSED`,
`TOO_MANY_PENDING_ORDERS`, `MODIFIER_RULES:<group>`, `INVALID_TRANSITION:a->b`
("This order was already updated by someone else" + refetch), `FORBIDDEN`,
`UNPAID_BALANCE`, `AMOUNT_EXCEEDS_DUE`, `TABLE_NOT_FOUND`, network errors.
Use `sonner` toasts for staff, inline messages for guests. Log unexpected errors with
a request id to the console in dev; leave a `reportError()` hook for Sentry later.

## 9. Security checklist
- RLS on every table (done in migration). Write tests for each role (pgTAP in
  `supabase/tests` or extend `db-smoke-test.mjs`).
- Secret key only in `admin.ts` (`server-only`). Grep CI step fails if
  `SUPABASE_SECRET_KEY` appears under `src/` outside `lib/supabase/admin.ts` / `lib/env.ts`.
- Security headers in `next.config.ts`: CSP (self, Supabase https + wss, Turnstile,
  `form-action` self + SSLCommerz hosts), `X-Frame-Options: DENY`, `Referrer-Policy:
  strict-origin-when-cross-origin`, `Permissions-Policy` (camera=(), geolocation=()).
- QR tokens are 32-char random; rotation invalidates old prints.
- Anti-abuse: DB caps (5 unconfirmed orders/session, 50 lines, qty ≤ 20), waiter
  confirmation gate before the kitchen, optional Turnstile on anonymous sign-in.
- Staff server actions re-check role on the server; never trust hidden UI.
- Validate uploads (type, ≤ 5 MB) — bucket also enforces it.

## 10. Testing strategy
- **DB**: `node docs/sql/db-smoke-test.mjs` (no Docker) + pgTAP tests via
  `supabase test db` for RLS per role.
- **Unit (Vitest)**: money formatting (en/bn digits), error mapping, cart store,
  table status priority, ETA calculation, SSLCommerz response parsing/validation logic.
- **Component**: item sheet modifier rules, cart stepper, slide-to-confirm (keyboard alt).
- **E2E (Playwright)** against local Supabase with `PAYMENT_GATEWAY=mock`:
  1. Full flow with three browser contexts (guest phone 390×844, waiter tablet
     1180×820, kitchen 1920×1080): scan → order → waiter confirm & send → kitchen
     start/ready → waiter served → guest tracker shows each step live → bill → mock
     online payment (IPN) → cash remainder → close → feedback.
  2. Two guests same table see each other's orders.
  3. Permissions: kitchen can't confirm; waiter can't open /admin; guest can't open /staff.
  4. Sold-out mid-cart → friendly error.
  5. Duplicate submit (double click / retry) creates one order.
  6. Axe accessibility scan on key pages (guest menu, tracker, bill, floor list, admin menu).
- CI (GitHub Actions): install → typecheck → lint → unit → db smoke test → build.
  E2E job with Supabase CLI (`supabase start`) on push to main.
